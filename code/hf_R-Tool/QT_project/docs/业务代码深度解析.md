# RFID Demo 常规业务代码深度解析

> 范围：本文解析 `hf_tagaccess` 中的业务模型、协议编解码、重试、日志、业务编排、界面协作，以及三份与业务直接相关的基础文件：`rfiddeviceadapter`、`CAEDevice_HF` 的业务桥接/稳定扫描部分、`gfunction`。不展开 SDK 头文件、`c++_lib`、驱动 DLL、`tests`、构建产物，也不逐行解释 `CAEDevice_HF` 中直接调用厂商 SDK 的底层盘点实现。

## 一、先建立全局地图

这个 Demo 的目标不是“读一个 RFID 块”这么简单，而是把一份有格式约束的业务数据安全地读写到 ISO15693 标签：

```text
界面输入 / 点击
    -> MainWindow：校验操作前置条件、展示状态
    -> RfidBusinessWorker：将一次业务请求包装为可重试任务
    -> RfidOperationRunner：尝试计数、延迟重试、取消
    -> RfidTagService：稳定标签、读写流程、写后校验、容量判断
    -> TagPayloadCodec：业务对象 <-> 标签字节协议
    -> RfidDeviceAdapter：业务层看到的设备接口
    -> CAEDevice_HF：SDK 参数转换、句柄/块读写桥接
    -> RFID SDK / 读写器
```

这张图比记住某个函数更重要。它体现了三类边界：UI 不拼字节，业务服务不直接碰 SDK，设备适配器不理解“病历号、姓名”等业务字段。

## 二、`rfidtagtypes.h`：跨层统一的数据语言

### 模块总览

该文件定义所有业务层共享的值对象。把它们抽出来，`MainWindow`、服务层、设备适配层就不会通过一长串零散参数协作。

```cpp
struct TagPayload
{
    quint8 formatVersion = 1;
    quint8 dishNumber = 0;
    QDateTime inseminationTime;
    QString femaleName;
    QByteArray medicalRecordNumber;
};
```

- `formatVersion` 是协议演进开关。以后字段变更时应新增版本，而不是让新旧数据“猜着解析”。
- `dishNumber` 用 `quint8`，明确其存储范围为 `0..255`。
- `QDateTime`、`QString` 是上层的强类型表达；编码时才降为 BCD 与 GBK 字节。
- 病历号刻意使用 `QByteArray`，因为协议定义它是 ASCII **原始字节**，长度也必须按字节而不是 `QString` 字符数计算。

```cpp
enum class RfidErrorKind {
    None, InputInvalid, ReaderNotReady, InventoryTimeout,
    TagNotUnique, TagConnectFailed, ReadFailed, WriteFailed,
    VerifyFailed, UnsupportedFormat, InvalidPayload,
    CapacityExceeded, Cancelled,
};
```

这不是普通错误码枚举，而是重试策略的输入。`ReadFailed` 可重试，`InputInvalid` 不可重试；这样业务代码不必从 SDK 数字错误码中推测语义。

```cpp
struct RfidOperationResult
{
    bool success = false;
    bool payloadDecoded = false;
    RfidErrorKind errorKind = RfidErrorKind::None;
    int sdkErrorCode = 0;
    int attemptCount = 0;
    QString message;
    QByteArray rawData;
    TagPayload payload;
};
```

`success` 表示操作是否成功；`payloadDecoded` 则把“底层成功读到字节”与“这些字节符合当前业务协议”分开。标签有旧格式时，应用仍能展示 HEX，而不把它误报成通信失败。这是很实用的兼容性设计。

`TagSystemInfo` 保存标签真实块大小、块数；`RfidDeviceResult` 保存设备层结果。二者避免业务层依赖厂商 SDK 类型。最后的 `Q_DECLARE_METATYPE` 让 `RfidOperationResult` 可以通过 Qt 跨线程信号传递。

### 架构沉淀

面试中可概括为：**用领域结果对象承载业务语义，用设备结果对象承载基础设施语义，避免把 SDK 错误码泄漏到 UI。**

## 三、`tagpayloadcodec`：协议唯一真相源

### 模块总览

这里规定标签内字节的排布、输入约束和人类可读的 HEX。它不依赖窗口和设备，因而最适合单测，也是业务正确性的核心。

### 常量与错误出口

```cpp
static const quint8 FormatVersion = 0x01;
static const int HeaderFieldLength = 2;
static const int HeaderLength = 16;
static const int NameLength = 8;
static const int MaxMedicalRecordLength = 64;

static void setError(QString *error, const QString &message)
{
    if (error)
        *error = message;
}
```

前两个字节是版本与长度，接着 1 字节皿序号、5 字节时间、8 字节姓名，所以固定头长为 `2 + 1 + 5 + 8 = 16`。`setError` 允许调用方只关心布尔结果，也可按需取得可展示的原因。

### 病历号校验

```cpp
if (record.isEmpty() || record.size() > MaxMedicalRecordLength)
    return false;
for (char ch : record) {
    const bool valid = (ch >= 'A' && ch <= 'Z') || ...
            || (ch >= '0' && ch <= '9') || ch == '_' || ch == '-';
    if (!valid)
        return false;
}
```

先检查长度，再逐字节白名单校验。这里不用“不是非法就放行”的黑名单，是因为协议要求 ASCII；白名单能避免空格、中文、控制字符或 UTF-8 多字节混入长度字段。

### BCD 时间的双向转换

```cpp
const QString digits = dateTime.toString("yyMMddHHmm");
for (int i = 0; i < digits.size(); i += 2)
    bcd.append(char((digits.at(i).digitValue() << 4)
                    | digits.at(i + 1).digitValue()));
```

例如 `2301311743` 变为 `0x23 0x01 0x31 0x17 0x43`。每两个十进制数字不是 ASCII 的 `'2'`、`'3'`，而是压入高、低四位。这正是 BCD 的含义。前面的年份范围 `2000..2099` 保证两位年份的解释不含糊。

```cpp
if (!isBcdByte(value)) return false;
digits += QString::number(value >> 4);
digits += QString::number(value & 0x0f);
const QDate date(2000 + digits.mid(0, 2).toInt(), ...);
const QTime time(...);
if (!date.isValid() || !time.isValid()) return false;
```

解码不能只看半字节是否 `0..9`；`0x19` 虽是合法 BCD，却不是合法月份，所以又交给 `QDate`/`QTime` 校验。**字节结构合法不等于业务值合法。**

### GBK 姓名字段

```cpp
QTextCodec *codec = QTextCodec::codecForName("GBK");
const QByteArray gbk = codec->fromUnicode(name);
if (gbk.contains('?') && !name.contains('?')) return false;
if (gbk.size() > NameLength) return false;
*encoded = QByteArray(NameLength - gbk.size(), ' ') + gbk;
```

`QString` 内部是 Unicode，但协议指定 GBK，因此先编码再判断 **字节数**。常见汉字通常占两字节，所以“4 个汉字”只是大致经验，真正约束是 8 字节。`?` 探测尽量阻止无法表示的字符静默替换。最后用前导空格补齐，读取时对应地只去掉前导空格。

```cpp
while (firstContentByte < encoded.size()
       && encoded.at(firstContentByte) == ' ')
    ++firstContentByte;
```

这段循环与写入的左填充严格配对；若全部是空格，姓名实际为空，应拒绝。

### 编码、解码与块填充

```cpp
const int totalPayloadLength = HeaderFieldLength + 1 + time.size()
        + name.size() + payload.medicalRecordNumber.size();
result.append(char(payload.formatVersion));
result.append(char(totalPayloadLength));
result.append(char(payload.dishNumber));
result.append(time);
result.append(name);
result.append(payload.medicalRecordNumber);
```

编码的关键是第二字节写入**总 payload 长度**，包含版本和长度字段本身。其余 append 顺序就是协议偏移量。`reserve` 只是预分配容量，减少扩容，不改变数据语义。

```cpp
const bool usesWholePayloadLength = raw.size() == lengthField;
const bool usesLegacyContentLength = raw.size() == lengthField + HeaderFieldLength;
```

解码同时兼容新格式（长度是总长度）和旧格式（长度是内容长度）。这解释了为什么代码没有先强制 `version == FormatVersion`：当前实现选择“尽量读出兼容数据”，由上层决定如何提示。注意这也使版本字段没有真正的版本分派能力，是未来应补的边界。

```cpp
const int remainder = payload.size() % blockSize;
*padded = payload;
if (remainder)
    padded->append(QByteArray(blockSize - remainder, '\0'));
```

标签按块写，payload 却是连续变长字节。这里向上补 `0x00`，但长度字节仍保存真实长度，所以读取只解析有效载荷，不会把填充当成病历号。

### 架构沉淀

编解码器要具备“输入校验、固定布局、兼容读取、纯函数化”四个特征。它现在做得基本正确；下一步应让 `formatVersion` 参与明确的版本分派，避免不同版本仅靠长度猜测。

## 四、`rfidretrypolicy` 与 `rfidoperationrunner`：把失败变成可控状态机

### 模块总览

策略类回答“该不该重试、等多久”；执行器回答“何时执行、何时结束、如何通知 UI”。拆开后，重试规则可测试，执行器也不懂 RFID。

```cpp
bool RfidRetryPolicy::isRetryable(RfidErrorKind kind)
{
    switch (kind) {
    case ReaderNotReady: case InventoryTimeout: case TagNotUnique:
    case TagConnectFailed: case ReadFailed: case WriteFailed: case VerifyFailed:
        return true;
    case None: case InputInvalid: case UnsupportedFormat: case InvalidPayload:
    case CapacityExceeded: case Cancelled:
        return false;
    }
}
```

可恢复问题才重试：读写失败可能是瞬时通信波动；输入非法、容量不足、用户取消则重试没有意义。`switch` 穷举 enum，比多个布尔条件更方便审计。

```cpp
return failedAttempt >= 1 && failedAttempt < MaxAttempts
       && isRetryable(errorKind);
```

`failedAttempt` 是刚刚失败的第几次。三次上限意味着第 1、2 次失败可以继续，第 3 次失败立即结束。延迟为 300 ms、500 ms，避免瞬间重发压垮设备。

```cpp
void RfidOperationRunner::start(const Operation &operation, bool retryEnabled)
{
    if (m_running || !operation) return;
    m_operation = operation; m_attempt = 0; m_cancelled = false;
    m_retryEnabled = retryEnabled; m_running = true;
    executeAttempt();
}
```

这段先拒绝重入，再重置本次运行状态。`Operation` 是 `std::function<RfidOperationResult()>`，所以 Runner 可被复用于读、写或初始化。

```cpp
if (m_cancelled) {
    result.errorKind = RfidErrorKind::Cancelled;
    result.attemptCount = m_attempt;
    m_running = false;
    emit finished(result);
    return;
}
++m_attempt;
emit attemptStarted(m_attempt);
```

取消在一次尝试开始前生效，因此不会凭空增加尝试数。先递增再发 `attemptStarted`，保证日志显示从 1 开始。

```cpp
try { result = m_operation(); }
catch (const std::exception &exception) { ... }
catch (...) { ... }
```

边界层使用异常兜底很合理：任何未捕获异常都必须转换为结果，而不能让 Qt 事件循环崩溃。这里统一归为 `ReadFailed` 有些粗糙，但至少会被记录和受重试策略控制。

```cpp
QTimer::singleShot(delayMs, this, [this]() { executeAttempt(); });
```

这是非阻塞延迟，不会用 `sleep` 卡住该对象所属事件循环。重点是：它只能保证“等待不阻塞”，不能自动保证底层读写不阻塞。

### 架构沉淀

重试不是 `for` 循环加 `sleep`。可靠实现应让错误分类决定重试资格，让尝试次数和事件通知成为显式状态。

## 五、`rfiddeviceadapter`：为什么它必须纳入学习范围

### 模块总览

这正是业务层与硬件层的防腐层。`RfidTagService` 只依赖抽象接口，因此可用 fake adapter 做测试，也不会了解 `ISO15693_*` API。

```cpp
class RfidDeviceAdapter
{
public:
    virtual ~RfidDeviceAdapter() = default;
    virtual RfidDeviceResult setAccessAntenna(quint32 antenna) = 0;
    virtual RfidDeviceResult connectIso15693(quint32 tagType, const QString &uid) = 0;
    virtual RfidDeviceResult disconnectTag() = 0;
    virtual RfidDeviceResult getSystemInfo(TagSystemInfo *systemInfo) = 0;
    virtual RfidDeviceResult readBlocks(...) = 0;
    virtual RfidDeviceResult writeBlocks(...) = 0;
};
```

每个纯虚函数都是服务层的“最低硬件需求”。这里没有 `QWidget`、没有 SDK 结构体，参数均是业务可理解的类型。虚析构函数保证用基类指针删除派生对象时行为正确。

```cpp
CaeRfidDeviceAdapter::CaeRfidDeviceAdapter(void *reader, void *connectedTag)
    : m_reader(reader), m_tagHandle(connectedTag) {}

CaeRfidDeviceAdapter::~CaeRfidDeviceAdapter()
{
    disconnectTag();
}
```

构造器接收已建立的会话；析构器兜底释放**自己拥有**的句柄。`void *` 降低了头文件对 SDK 的耦合，但牺牲了类型安全，长期更好的做法是把 SDK 句柄封在 `.cpp` 私有实现里。

```cpp
if (m_tagHandle)
    return RfidDeviceResult {true, 0, QString()};
```

已有外部会话时不重复设置天线或连接标签，因为某些驱动会让重设天线使既有句柄失效。这是典型的“设备兼容性规则”，放适配器而非业务服务是正确位置。

```cpp
const RfidDeviceResult result = CAEDevice_HF::connectIso15693(..., &tagHandle);
if (result.success) {
    m_tagHandle = tagHandle;
    m_ownsTagHandle = true;
}
```

只有本适配器创建的句柄才设置 `m_ownsTagHandle`。`disconnectTag()` 据此避免销毁由 `MainWindow` 创建的 `ht`；否则业务读写结束会让 UI 持有悬空会话。

### 架构沉淀

这个文件不是应排除的“驱动细节”，而是必须掌握的**依赖倒置接口**。真正应排除的是它委托到 SDK 的机械调用实现。

## 六、`rfidtagservice`：读写业务的核心编排

### 模块总览

服务层负责稳定性判定、容量规划、读取、写入和写后验证。它是“业务规则中心”，同时把设备异常映射为 `RfidOperationResult`。

### 稳定扫描判定

```cpp
QString observationKey(const InventoryObservation &o)
{
    return o.uid + '|' + QString::number(o.airProtocol)
           + '|' + QString::number(o.antenna);
}
```

同一 UID 但协议或天线变化也不算同一个稳定观测。这样避免将移动、跳天线或协议识别异常的标签误认稳定。

```cpp
for (const InventoryObservation &o : observations) {
    if (o.deviceError) { ... return result; }
    if (o.uid.isEmpty()) continue;
    ++appearances[key];
    latestObservation.insert(key, o);
    uniqueUids.insert(o.uid);
}
```

设备错误优先中止，因为继续汇总已无意义；空 UID 是无效观测，跳过；哈希表统计出现次数，集合统计 UID 去重数。

```cpp
if (uniqueUids.size() > 1) { state = TagNotUnique; ... }
if (appearances.isEmpty()) { state = TagTimeout; ... }
if (appearances.size() != 1) { state = TagDetected; ... }
```

判定顺序很重要：多 UID 必须拒绝自动选择；无有效 UID 是超时；只有一个 UID 却跨协议/天线则视为尚不稳定。

```cpp
if (result.appearanceCount >= StableAppearanceCount)
    result.state = TagStabilityState::TagStable;
```

**Code Review 重点：当前 `StableAppearanceCount = 1`，但 SPEC 与 UI 提示都写“1000 ms 内至少出现 2 次”。**这会让只出现一次的标签被服务层判为稳定。应把常量改为 `2`，并补充边界测试（1 次不稳定、2 次稳定）。

### 写入计划与容量

```cpp
if (systemInfo.blockSize <= 0 || systemInfo.blockCount <= 0)
    return false;
TagPayloadCodec::padForBlocks(payload, systemInfo.blockSize, &padded, &error);
const qint64 capacity = qint64(systemInfo.blockSize) * systemInfo.blockCount;
if (padded.size() > capacity) { errorKind = CapacityExceeded; return false; }
plan->blockCount = padded.size() / systemInfo.blockSize;
```

先拿真实系统信息，再补齐数据，再比较容量。`qint64` 防止两个 `int` 相乘先溢出；这是处理设备容量时容易忽略的防御式细节。

### 读取：先头块，后按长度精确读取

```cpp
deviceResult = readRange(0, 1, &raw);
const int lengthField = raw.size() > 1 ? quint8(raw.at(1)) : 0;
const bool wholeLengthPossible = ...;
const bool legacyLengthPossible = ...;
```

先读一个块获取长度，避免每次都读取整张标签。若长度符合新/旧协议候选值，再算所需块数读取剩余内容；若不符合，才完整读取后作为“原始数据”展示。这是性能与兼容性之间的折中。

```cpp
if (raw == QByteArray(raw.size(), '\0')) {
    result.errorKind = UnsupportedFormat;
    result.message = "The tag is blank...";
    return result;
}
```

空白标签和通信读失败必须区分：前者提示用户初始化，不应无脑重试。

```cpp
if (!TagPayloadCodec::decode(result.rawData, &result.payload, &error))
    return rawDataReadResult(raw, error);
result.success = true;
result.payloadDecoded = true;
```

解码失败并不丢掉已经读到的数据，`rawDataReadResult` 把结果标为成功但 `payloadDecoded=false`。这使 UI 能安全地展示未知格式标签，而不改写它。

### 写入：先编码、再写块、最后读回校验

```cpp
if (!TagPayloadCodec::encode(payload, &encoded, &error)) {
    result.errorKind = InputInvalid;
    return result;
}
```

输入校验在碰硬件前完成，因此 `InputInvalid` 不进入重试。

```cpp
if (dataToWrite.size() + HeaderFieldLength <= paddedCapacity)
    dataToWrite.append(QByteArray(HeaderFieldLength, '\0'));
```

这会清零 payload 后紧邻的两字节，防止旧固件留下的内容长度尾部让新格式被误判为旧格式。它是兼容历史数据的“写入清尾”策略。

```cpp
deviceResult = device->writeBlocks(0, plan.blockCount, ...);
if (!deviceResult.success) {
    RfidOperationResult confirmation = readPayload(device, tag);
    if (confirmation.success && confirmation.rawData.startsWith(encoded))
        return confirmation;
    return deviceFailureResult(deviceResult, RfidErrorKind::WriteFailed);
}
```

**这段非常值得记住。**设备可能已写成功，但回包丢失。直接重试写会造成重复或覆盖风险，所以先读回确认，确认成功即按成功处理。

```cpp
RfidOperationResult verification = readPayload(device, tag);
if (!verification.rawData.startsWith(encoded)) {
    verification.success = false;
    verification.errorKind = RfidErrorKind::VerifyFailed;
}
```

成功的定义不是 SDK 返回成功，而是“读回内容以前缀形式与编码 payload 相等”。后面允许有块填充 `0x00`，故不能简单比较完整块数据。

### 架构沉淀

服务层体现了可靠 I/O 的基本套路：**前置校验 -> 建立会话 -> 获取能力信息 -> 最小读取/写入 -> 读后验证 -> 语义化结果。**

## 七、`rfidbusinessworker`：任务外壳与当前线程问题

### 模块总览

它把同步的服务调用放进一套带局部事件循环的重试机制，并把尝试、延迟、完成事件转发给 UI。

```cpp
RfidOperationRunner runner;
*runnerSlot = &runner;
QEventLoop loop;
QObject::connect(&runner, &RfidOperationRunner::finished, &loop,
    [&](const RfidOperationResult &value) { result = value; loop.quit(); });
QTimer::singleShot(0, &runner, [&runner, operation, retryEnabled]() {
    runner.start(operation, retryEnabled);
});
loop.exec();
```

`runner` 是栈对象，`runnerSlot` 只在局部事件循环期间有效。`singleShot(0)` 是一个细致处理：若直接 `start()`，同步完成时 `finished` 可能早于 `loop.exec()` 发出，导致本地循环永不退出。延后到事件循环启动后可消除竞态。

```cpp
CaeRfidDeviceAdapter device(reader, connectedTag);
const RfidOperationResult result = RfidTagService::readPayload(&device, tag);
```

Worker 每次尝试创建短生命周期适配器。若传入的是 UI 已连接的标签句柄，适配器并不拥有它，不会在析构时断开它。

```cpp
void RfidBusinessWorker::cancel()
{
    requestCancel();
    if (m_runner) m_runner->cancel();
}
```

这里的 `m_cancelRequested` 当前只被赋值、未被读；实际取消依赖 `RfidOperationRunner::m_cancelled`，并只会在下一次尝试前生效。

**Code Review 重点：`businessWorker = new RfidBusinessWorker(this)` 没有 `moveToThread`，而 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 只是把调用排回 Worker 所在线程，也就是 UI 线程。**因此一次同步 SDK 读写仍可能冻结界面；局部 `QEventLoop` 虽能处理定时器，却没有把阻塞 I/O 变成后台 I/O。修复方向是专门的业务 `QThread`，在打开设备后创建/移动 Worker，关闭前请求取消并 `quit()/wait()`。

### 架构沉淀

异步调用与后台执行不是同义词。判断线程是否真的隔离，应检查 QObject 的 thread affinity，而不是只看 `QueuedConnection`。

## 八、`rfidlogger` 与 `rfidlogdispatcher`：可观测性与脱敏

### 模块总览

日志被拆为格式化（纯函数）与投递（UI、控制台、文件）两部分，既便于测试，也让隐私策略集中。

```cpp
QString line = QStringLiteral("[%1][%2][%3][%4] %5")
    .arg(time.toString("yyyy-MM-dd HH:mm:ss.zzz"))
    .arg(levelName(level)).arg(stage).arg(attempt).arg(message);
for (auto it = fields.constBegin(); it != fields.constEnd(); ++it)
    line += QStringLiteral(" %1=%2").arg(it.key(), it.value());
```

输出统一为时间、级别、阶段、尝试次数、正文与键值字段。`QMap` 令字段按键排序，利于日志对比。

```cpp
return name.left(1) + "***";
return value.size() <= 4 ? value : "***" + value.right(4);
```

姓名只保留首字符；病历号只保留末四位。UI 可显示完整数据供当次人工核对，但落盘日志默认应脱敏。

```cpp
emit entryAdded(line);
if (!m_fileLoggingEnabled) return;
...
stream << RfidLogger::format(level, stage, attempt, message,
                             redactForFile(fields)) << '\n';
```

先发完整 `entryAdded` 给当前界面，再将脱敏字段写文件。`redactForFile` 中仅在显式开启 `m_sensitiveDebugEnabled` 时返回原文。

**Code Review 重点：构造函数里默认调用 `setFileLoggingEnabled(true, logFilePath)`，而 SPEC 写“本地文件日志默认关闭”。**实际字段会脱敏，风险较低，但与需求不一致；应改为默认关闭，并在 UI 或配置中由用户显式开启。

### 架构沉淀

日志不是附属输出。对包含个人数据的系统，应将“展示日志”和“持久化日志”的权限、脱敏策略分开设计。

## 九、`MainWindow`：UI 只负责触发、约束与呈现

### 模块总览

`MainWindow` 历史上混有较多直接 SDK 操作；本文只解析新增业务读写路径。传统块读写、EAS、AFI、驱动加载等硬件交互不属于本文逐行范围。

### 初始化业务组件和信号关系

```cpp

create_business_view();
businessLogger = new RfidLogDispatcher(this);
businessWorker = new RfidBusinessWorker(this);
connect(businessWorker, &RfidBusinessWorker::completed,
        this, &MainWindow::on_business_completed);
```

注册元类型是跨线程信号的前提；创建视图后构造日志和 Worker，并将 Worker 的状态信号接回 UI。父对象为 `this` 保证窗口销毁时组件一并销毁。

```cpp

    && !businessOperationRunning && accessTagSource == AccessTagSource::ScanMode
    && businessScanStable && m_tags_hf.size() == 1;
```

这是业务按钮的状态机。它同时要求读写器、标签会话、非盘点、非读写中、来自业务扫描、稳定、唯一。把条件集中在一个函数中，避免多个 slot 各自漏掉状态。

### 发起读取

```cpp

... // 禁用两个业务按钮
void *reader = hr;
void *connectedTag = ht;
businessOperationRunning = true;
businessReadOperation = true;

    worker->read(reader, connectedTag, tag);
}, Qt::QueuedConnection);
```

先抓取标签快照，再禁用操作，再保存句柄与模式位，最后排队执行。快照避免异步任务开始前 UI 中选中项变化；`businessReadOperation` 让完成处理知道该显示读取字段还是写入结果。

### 发起写入

```cpp
medicalRecord->setValidator(new QRegularExpressionValidator(
    QRegularExpression("[A-Za-z0-9_-]{0,64}"), medicalRecord));
...

    QMessageBox::warning(this, "写入业务数据", error);
```

Validator 提升输入体验，但不能作为安全校验：程序可从其他路径构造 `TagPayload`，所以仍要调用编解码器做最终校验。这是“UI 校验 + 领域校验”双层防线。

```cpp
    return;
```

### 完成后的两种读取结果

```cpp

        && !result.payloadDecoded && !result.rawData.isEmpty();
```

“成功读到未知格式原始数据”不是错误。这一判断直接对应服务层的双状态设计。

```cpp

    // 用表格展示五个业务字段，并展示原始 HEX

```

可解码时展示结构化字段；否则展示错误或 raw HEX。两条展示路径清楚地保护了旧格式标签，避免用户看到“读取成功”后又被误导为“格式正确”。

### 业务扫描到可读写的状态流转

```cpp

...

```

启动扫描先让旧会话失效、清空旧列表、标记不稳定，再让 `CAEDevice_HF` 在工作线程执行 1000 ms 窗口扫描。

### 架构沉淀

UI 的最佳职责是：收集输入、表达状态、发出命令、呈现结果。这里新增的业务路径基本遵守这一点；下一步应把遗留的直连 SDK 代码继续迁入 adapter/service。

## 十、`CAEDevice_HF`：只解析业务相关桥接与稳定扫描

### 模块总览

它既有遗留底层盘点代码，也新增了被业务层调用的静态设备桥接。前者不在本文逐行范围；后者是设备边界的一部分，需要理解。

```cpp
RfidDeviceResult CAEDevice_HF::connectIso15693(..., const QString &uid,
                                                RFID_TAG_HANDLE *tagHandle)
{
    if (reader == nullptr || tagHandle == nullptr) return deviceFailure(...);
    const QString normalizedUid = uid.trimmed();
    if (normalizedUid.size() != 16 || !hex16.match(normalizedUid).hasMatch())
        return deviceFailure(...);
    QByteArray uidBytes = QByteArray::fromHex(normalizedUid.toLatin1());
    *tagHandle = nullptr;
    const int sdkResult = ISO15693_Connect(reader, tagType, 1,
        reinterpret_cast<BYTE *>(uidBytes.data()), tagHandle);
    return sdkResult == NO_ERR ? deviceSuccess() : deviceFailure(...);
}
```

这个桥接层先验证业务输入，再转换为 SDK 所需的 8 字节 UID 和指针，最后把整数返回码转换成 `RfidDeviceResult`。关键是对外不泄漏 `RFID_TAG_HANDLE` 的创建细节。

```cpp
const qint64 byteCount = qint64(blockCount) * blockSize;
if (byteCount > INT_MAX) return deviceFailure(...);
QByteArray buffer(int(byteCount), 0);
...
if (blocksRead != DWORD(blockCount) || bytesRead != DWORD(buffer.size()))
    return deviceFailure(...);
```

读块桥接不仅检查 SDK 返回成功，还验证“实际读块数、实际字节数”恰好符合请求。设备 I/O 中这一步很重要，因为“没有报错”仍可能返回短数据。

```cpp
// 先尝试多块写
sdkResult = ISO15693_WriteMultipleBlocks(...);
if (sdkResult == NO_ERR) return deviceSuccess();
// 失败后逐块写
for (int index = 0; index < blockCount; ++index)
    sdkResult = ISO15693_WriteSingleBlock(...);
```

ISO15693 要求支持单块写、多块写是可选能力，因此逐块回退是合理的兼容策略。它应留在硬件桥接层，业务层只需要知道“写成功或失败”。

```cpp
while (timer.elapsed() < ScanWindowMs) {
    m_tags_hf.clear();
    iret = runInventoryRound(firstRound);
    ...
    observations.append(observation);
    ...
    QThread::msleep(qMin(InterRoundDelayMs, remainingMs));
}
const StableInventoryResult stable =
    RfidTagService::evaluateInventoryWindow(observations);
```

该循环属于业务扫描：在 1000 ms 内重复获得底层观测，转换为 `InventoryObservation`，最终把“稳定”这个业务判断委托给 `RfidTagService`。`msleep` 位于设备工作线程而非 UI 线程，所以不会直接卡界面。

### 架构沉淀

`CAEDevice_HF` 目前是过渡型类：既做设备控制又做部分扫描编排。理想演进是将纯设备调用保留在 adapter，将“窗口内稳定性策略”完全迁到 service，令它只产出原始观测。

## 十一、`gfunction`：小工具也有工程边界

### 模块总览

它提供十六进制转换和 ANSI/Unicode 转换。虽然不是 RFID 驱动，仍是旧 UI/SDK 调用链的一部分。

```cpp
for (i = 0; i < bLen; i++) {
    r4b = bBuffer[i] & 0x0f;
    l4b = (bBuffer[i] & 0xf0) >> 4;
    strBuf[i * 2] = l4c;
    strBuf[i * 2 + 1] = r4c;
}
```

每个字节拆为高、低四位并分别映射到 `0-9A-F`，所以输出缓冲区至少需 `bLen * 2 + 1`。函数本身没有写终止符，调用方必须事先清零或自行补 `\0`。

```cpp
if (byLen > 0 && byteCount > byLen)
    byteCount = byLen;
```

这里会**静默截断**超出缓冲区容量的输入，返回仍是 `true`。作为显示工具尚可，但作为写标签输入解析很危险；新版 `MainWindow::parseHexInput` 已改为严格长度检查，应优先使用新版。

```cpp
wchar_t *result = (wchar_t *)malloc(...);
mbstowcs(result, str, textlen);
```

这两组转换函数把内存所有权交给调用者，且依赖当前 locale，不能可靠处理任意中文。Qt 代码中优先使用 `QString::fromLocal8Bit`、`toLocal8Bit` 或明确的 `QTextCodec`；避免继续扩散这套裸指针 API。

### 架构沉淀

工具函数应有清晰的缓冲区契约和编码约定。新业务路径已经通过 `QByteArray`、`QString`、`TagPayloadCodec::toHex` 绕开了这些风险，这个方向是正确的。

## 十二、建议的阅读与面试复盘顺序

1. 先手算一份 `TagPayload` 的字节布局，再读 `TagPayloadCodec::encode/decode`。
2. 接着模拟一次“写回包丢失”：理解为什么 `writePayload` 必须读回确认。
3. 画出 `RfidErrorKind -> RfidRetryPolicy` 的可重试映射。
4. 从 `MainWindow` 点“写入”一路跟到 `CAEDevice_HF::writeBlocks`，确认每层只承担自己的职责。
5. 优先修复三项问题：稳定阈值改为 2、Worker 移入专用线程、文件日志默认关闭；然后补对应测试。

真正掌握这个 Demo 的标志，不是能背出 SDK 函数，而是能解释：为什么协议编码与设备操作隔离、为什么读写要验证、为什么重试依赖错误分类，以及为什么 Qt 的排队调用不必然等于后台执行。
